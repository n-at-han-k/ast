# gtk-ast

GIR is GTK's own API description, and gobject-introspection publishes a formal grammar for the
format. That grammar is the spec these node types are generated from, the same way `markdown-ast`
generates from `CommonMark.dtd`.

```sh
ruby work/gtk-ast/extract_gir.rb --write     # nix store -> work/gtk-ast/gir (15 files, gitignored)
ruby work/gtk-ast/grammar.rb                 # gir-1.2.rnc -> rng -> grammar rules
ruby work/gtk-ast/build_config.rb            # grammar rules -> config.yml
ruby work/gtk-ast/generate.rb                # config.yml -> node.rb
ruby work/gtk-ast/generate.rb --check        # fails if node.rb is stale
ruby work/gtk-ast/parse.rb Gtk-4.0           # parse a .gir into the typed AST
```

Run inside `nix develop .#gtk`, which supplies `GIR_PATH` and `rnc2rng`.

## The three artifacts, which are easy to confuse

| | what it is | size |
| --- | --- | --- |
| `gir-1.2.rnc` | the **grammar** of the `.gir` format, in RELAX NG Compact. One file, applies to every `.gir` | 786 lines |
| `Gtk-4.0.gir` | the **data**: GTK's API in that format, generated by `g-ir-scanner` from C sources | 8.4M |
| `Gtk-4.0.typelib` | the same data compiled by `g-ir-compiler` for runtime lookup, documentation stripped | 568K |

The `.gir` is the source artifact and the typelib is derived from it — not the other way round.
blueprint-compiler reads the typelib because it already has `gi` bindings and wants fast lookups,
then falls back to the `.gir` for the one thing the typelib drops: documentation. We parse the
`.gir`, because it is the superset and nokogiri can read it.

## Pipeline

`rnc2rng` converts the grammar to RELAX NG XML, and `grammar.rb` parses that with nokogiri pattern
matching — nokogiri being the only Ruby XML library with `deconstruct_keys`. The grammar yields 37
element definitions and 5 attribute groups, which `build_config.rb` writes as `config.yml`: 37
nodes, 260 fields, 92 child relations, 67 enumerated domains.

Every field records what the grammar states, including the XML attribute it comes from:

```yaml
- name: Property
  element: core:property
  fields:
  - {name: name,           attribute: name,           type: string, required: true}
  - {name: construct_only, attribute: construct-only, type: text, domain: ['0','1'], required: false}
  children: [...]
  groups: [Info.attrs, TransferOwnership, Info.elements, AnyType]
```

Attribute groups are mixins — `Info.attrs` carries `introspectable`, `deprecated`,
`deprecated-version`, `version`, `stability` — and `build_config.rb` merges them into each node that
references them, which is why `Class` ends up with more fields than the `Class` definition declares
on its own.

## What the grammar bought

The hand-rolled parser this replaced read `<property>`, `<implements>` and `<glib:signal>` and
nothing else. Parsing the same file against the grammar:

```
Gtk-4.0.gir parsed in 0.6s
  26614 nodes across 32 types

  Type 6683   CallableParams 5172   CallableReturn 4941   Method 3348
  Property 1303   Member 802   Field 722   FunctionMacro 638
  Implements 518   Callback 456   Signal 348   VirtualMethod 323
  Constructor 322   Class 269
```

`Gtk.Widget` has 244 children — 164 methods, 35 properties, 25 virtual methods, 13 signals, 3
implements, 2 functions, 2 fields. Only the 35 properties were being read before.

Nodes pattern match directly:

```ruby
case child
in GirAst::Property(name:, writable: "1")   then "read-write property #{name}"
in GirAst::Method(name:, identifier:)       then "method #{name} -> #{identifier}"
in GirAst::Implements(name:)                then "implements #{name}"
end
```

Note that `Class` and `Method` must be written `GirAst::Class` and `GirAst::Method` outside the
module: Ruby's own `::Class` and `::Method` are constants on `Object`, and `include GirAst` does not
override them, so an unqualified `in Class(name: "Box")` silently matches nothing.

## Containment is not in the grammar

The grammar says what a `.gir` document may contain — that `<class>` may hold `Method*`,
`Property*`, `Field*`. It says nothing about what a *widget* may contain at runtime, because GIR
describes an API, not a widget tree. GTK models that tree as a `parent` property plus
`first_child`/`next_sibling` accessors on `Gtk.Widget`, and the rules about which widgets accept
which children live in each widget's C `buildable_add_child`.

`reference/readme.md` records the closed list of widgets with requirements beyond "any number of
children", taken from blueprint-compiler, which hand-writes a module per widget for exactly those.
